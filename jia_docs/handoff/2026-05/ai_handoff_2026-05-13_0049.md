## 7. 推荐的后续接手顺序

建议后续接手者按下面顺序推进，而不是继续无差别改动：

### 第一步：先冻结当前可编译状态

先做以下事情：

- 备份当前三份底盘文件和当前构建日志。
- 明确哪些文件属于本轮真正功能改动，哪些只是编码污染。
- 尤其分离：
  - 四舵轮功能并入改动
  - 注释/编码/BOM 清洗改动
  - IDE 配置改动

### 第二步：决定是否让 FSM 真正切换到底盘新对象

重点核查：

- `Finite_StateMachine.registerChassisSetup(&ChassisOmni);`

如果目标是“真正启用四舵轮控制路径”，需要明确：

- FSM 接口类型是否兼容 `FourSteerChassis`
- 是否需要新的 adapter / setup 封装
- 是否要让 `registerChassisSetup()` 改为注册新的 `chassis` 对象

这一项是功能层面的真实切换点，不是宏切换能自动解决的。

### 第三步：补真实参数

当上层控制链明确之后，再替换以下真实参数：

- 四模块几何坐标
- 各模块 `theta_oa_to_owi_deg`
- `steer_motor_sign`
- `drive_motor_sign`
- 回零传感器 IO
- 零位偏移
- 限速 / 限加速度参数

### 第四步：单独治理编码/BOM

建议单独开一个很小的整理步骤，只做：

- 确定项目真正需要的源码编码规范
- 批量统一到同一种编码
- 避免再出现“部分 UTF-8 BOM、部分 GB2312、部分控制台乱码回写”的状态

如果这一步不单独拆开，后面所有 `git diff` 都会非常难看，且容易误伤功能代码。
