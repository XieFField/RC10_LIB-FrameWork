## 1. 项目与比赛背景总览

这个工程属于 2026 年全国大学生机器人大赛 ROBOCON 相关电控代码的一部分，主控平台是 STM32H723。虽然项目主体面向 ROBOCON，但在代码架构、外设选择、通信方式、电机使用方式、上位机调试习惯等方面，与 RoboMaster 机甲大师比赛常见电控架构有很强相似性。

从本次上下文中已经明确的背景有：

- 你所在团队总体人数大约 20 到 30 人。
- 控制方向只是总团队的一个方向，此外还有机械结构、视觉处理、硬件电路等方向。
- 你当前主要负责的文件集中在底盘调试相关的四个文件内：
  - `User\Setup\Src\chassis.cpp`
  - `User\Setup\Inc\chassis.h`
  - `RC10_LIB\APP\Inc\APP_Utils.h`
  - `RC10_LIB\APP\Src\APP_Utils.cpp`
- 这次实际推进时，除了上述四个文件，出于“把真实硬件接进调试链路”的需要，也最小化改动了 `Setup_ConfigInit.cpp/.h`。

### 1.1 为什么说这个工程风格接近 RoboMaster

接近的原因不在“比赛规则相同”，而在以下工程习惯：

- 使用 CAN/FDCAN 作为主要电机与驱动器通信总线。
- DJI 电机（M3508/M2006/GM6020）封装方式明显带有 RoboMaster 电控的常见味道。
- 使用 FreeRTOS 做任务调度，底盘、接收机、传感器、外设驱动分模块组织。
- 用上位机浮点流（VOFA 风格）来做快速电机与控制环观测。
- 将“应用层命令生成”和“电机层执行/反馈解析”分开，形成 chassis -> motor -> bsp_can 这样的层级关系。
- 在调试流程上大量依赖“摇杆直控 + 上位机看目标/反馈 + 逐步替换为闭环”的方法。

### 1.2 为什么这对接手人重要

因为理解这个工程，不能只把它看成“某个函数为什么这么写”。更重要的是理解：

- 底盘层到底管什么。
- 电机层到底管什么。
- CAN 总线注册和调度机制是谁负责。
- VOFA 打印的值是“真实执行量”还是“上层期望量”。
- 校准零点是应该落在底盘层，还是落在电机层。

后文会围绕这些问题展开。

## 3. 当前硬件连接与调试对象的真实关系

这一部分是后续一切理解的基础。

### 3.1 单舵轮调试时的核心硬件映射

这次调试链路围绕的是**单个舵轮**，不是整车四个舵轮一起。

确认过的关键映射是：

- 舵向电机：`M3508`，当前实际挂在 `CAN1`，`ID = 1`
- 轮向电机：`VESC`，当前挂在 `CAN2`，`ID = 101`
- 舵向校准：使用光电门/光电传感器
- 主控：`STM32H723`
- 调试上位机：以 `VOFA` 风格浮点流为主
- 遥控接收：`CRSF` 路径存在，代码中通过 `Module_CrsfReceiver` 获取摇杆量

### 3.2 为什么不是 CAN3

在最早规划阶段里，曾经按“VESC 在 CAN2，M3508 在 CAN3”的思路讨论过方案。但用户随后明确更正：

- 现在用的 `M3508` 实际已经挂在 `CAN1` 上，且 `ID = 1`

因此，后续实现的正确接线语义是：

- 复用当前已经存在并注册在 `CAN1` 上的 `omni_wheel1`
- 在 `CAN2` 上新增并注册 `VESC_Motor vesc_drive_101`

这条更正非常重要。否则后续所有“为什么舵向电机没反馈/没控制”都会查错方向。

### 3.3 为什么要暂停 CAN2 原武器侧注册

因为 `CAN2` 在原工程里本来就已经挂了别的设备，典型包括：

- `Weapon_launchMotor`
- `Weapon_clawMotor`
- `Weapon_traverseMotor`
- `Weapon_wristMotor`
- `DJIGroupCAN2_Low`

单舵轮台架调试时，如果保留这些旧注册，那么会出现两个问题：

1. `CAN2` 会继续周期性调度并发送原武器侧控制帧，污染当前总线调试环境。
2. 你在观察 `VESC` 时，看到的不是一条干净的实验总线，而是“旧业务 + 新舵轮调试”混在一起。

因此，后续实现选择的是：

- 保留 `CAN1` 原注册不动
- 临时注释 `CAN2` 原武器侧注册
- 只向 `CAN2_Bus` 注册 `vesc_drive_101`

这样台架调试期的 `CAN2` 是干净的。
## 4. 关键类与分层关系

为了后续接手者少走弯路，这里把当前最重要的几层抽象拆开说。

### 4.1 `Motor_Base`：统一的电机抽象层

`Motor_Base` 的存在意义是：让上层底盘逻辑不用关心底层是 DJI 电机、VESC、DM 电机还是别的电机。

当前你需要记住的公共语义主要有：

- 目标量：
  - `target_current_`
  - `target_rpm_`
  - `target_angle_`
  - `target_totalAngle_`
- 反馈量：
  - `current_`
  - `rpm_`
  - `angle_`
  - `totalAngle_`
- 控制接口：
  - `setTargetCurrent(...)`
  - `setTargetRPM(...)`
  - `setTargetAngle(...)`
  - `setTargetTotalAngle(...)`

这使得 `FourSteerChassis::WheelConfig` 可以这样设计：

- 舵向侧用 `M3508* steer_motor_h`
- 轮向侧用 `Motor_Base* drive_motor_h`

也就是说：

- 舵向电机默认就是 DJI 位置/速度/电流一体化处理逻辑
- 轮向电机则允许以后换成 VESC、GO、DM 或别的实现

### 4.2 `Motor_DJI` / `M3508`

对你这次任务来说，最重要的点有：

1. `M3508::setTargetAngle(...)` 是单圈角度控制，内部角度环是 circular。
2. `M3508::setTargetTotalAngle(...)` 是多圈总角度控制，内部角度环是 linear。
3. `getAngle()` 返回当前单圈角。
4. `getTotalAngle()` 返回当前总角度。
5. `relocate_totalAngle(...)` 可以重定义零点。

`relocate_totalAngle(...)` 非常关键。它的语义不是“加个显示补偿”，而是：

- 直接让编码器累计位置与电机对象中的 `totalAngle_ / angle_` 进入新的参考系。

这也是后面讨论“校准零点下沉到电机层”时的理论基础。

### 4.3 `VESC_Motor`

当前 `VESC_Motor` 的真实状态要特别谨慎理解。

#### 它已经支持的内容：

- 目标电流模式
- 目标 RPM 模式
- 目标总角度命令接口（`setTargetTotalAngle`）
- 刹车电流模式
- 占空比模式
- `STATUS_1` 反馈解析

#### 它当前真正解析出来的反馈只有：

- `rpm_`
- `current_`
- `duty_`

也就是说，当前代码里 `VESC` 的角度接口虽然形式上存在：

- `getAngle()`
- `getTotalAngle()`
- `target_angle_`
- `target_totalAngle_`

但**真实角度反馈链路并没有在当前驱动中打通**。因此任何“轮向角度”打印、VOFA 通道、对比项，如果直接读 `Motor_Base` 默认角度接口，很可能只是 0 或无意义值。

这也是为什么在之前的讨论里，明确区分了：

- `VESC` 速度环调试：已经可做
- `VESC` 位置/角度相关反馈：当前不能当成已经可用

### 4.4 `Setup_ConfigInit`：对象实例化与接线层

这一层常常被初学者低估。

实际上一旦出现以下问题，就要回看 `Setup_ConfigInit.cpp`：

- `wheel.dmh` 为什么是空的
- `VESC` 为什么没收到报文
- 明明 `chassis.cpp` 在调某个轮子，为什么没反馈
- 为什么同样的逻辑换个电机对象就失效

因为这里负责的是：

- `fdCANbus *const CAN1_Bus / CAN2_Bus / CAN3_Bus`
- `M3508 omni_wheel1...`
- `VESC_Motor vesc_drive_101...`
- 注册到总线
- 传给底盘对象

没有这一层，`chassis.cpp` 再漂亮也只是空壳。

### 4.5 `FourSteerChassis::isDebugMode()`：当前单舵轮调试的核心现场

如果说这次工作最核心的入口函数是哪一个，那就是：

`User\Setup\Src\chassis.cpp` 里的 `FourSteerChassis::isDebugMode()`

原因：

- 摇杆输入在这里被读取
- 单个舵轮的调试目标在这里生成
- 舵向电机和轮向电机的命令在这里下发
- 光电门校准状态机在这里运行
- VOFA 打印也在这里组织

后续谁接手，谁就必须首先看懂这个函数，不然很容易出现：

- 改了某个 helper 但其实目标源逻辑没变
- 以为改的是执行命令，实际上只改了打印
- 以为看到的是目标单圈角，实际上看到的是补偿前原始角

### 5.4 为什么要动 `CAN2` 注册，而不是只在 `chassis.cpp` 里 new 一个对象

这个问题实际非常关键。

如果只是：

- 在 `chassis.cpp` 里多写一个 `Motor_Base*`
- 或多写几个 `setTargetRPM(...)`

但没有在初始化层：

- 实例化 `VESC_Motor`
- 注册到 `CAN2_Bus`
- 将其传给 `FourSteerChassis`

那么运行时 `wheel.dmh` 依然可能是空的，或者即使有对象，也根本不会被总线任务调度、不会收发 CAN 帧。

所以必须把 `VESC` 接入 `Setup_ConfigInit.cpp`。

### 5.5 摇杆映射的选择

用户明确确认过：

- `左 Y 控轮速`
- `右 X 控舵角`

这背后的原因很实际：

- 左摇杆前后更适合做“轮子快慢”连续调速
- 右摇杆横向更适合做“舵轮指向角”调试

### 5.6 死区问题的选择

曾经讨论过是否要加软件死区。

用户的观点是：

- 遥控器输出端已经做过死区
- 软件侧不需要再重复限制

因此后续策略是：

- 不额外加软件死区
- 不额外做“极小值自动归零保护”
- 目标量尽可能保留遥控器原始手感

这意味着若后续在实际板上看到轻微抖动、爬行，应该优先考虑：

- 遥控器死区是否真的生效
- 接收端是否仍有小量噪声
- VESC 自身速度环参数是否过于敏感

而不是先假定软件逻辑有 bug。

### 5.7 为什么后来又扩展到 VOFA 全量打印

最初只要求在 `chassis.cpp` 1100 行附近像 M3508 一样读出 VESC 报文并打印到上位机。

后续用户又提出：

- 希望能在 VOFA 中看到光电传感器情况
- 校准角度
- 舵向和轮向目标/反馈的电流、速度、单圈角、多圈角

因此打印帧逐步从“很少几个角度量”扩展成了一个更完整的 18 通道浮点帧。

但这同时也暴露了另一个事实：

- `VESC` 当前只有速度和电流反馈真实可用
- “轮向角度”接口虽然形式上可打印，实际上并没有真实反馈支撑

这点在后文第 8 章会展开。

### 5.8 关于“统一目标生成器”的重构

用户进一步提了一个非常合理的问题：

> 如果我想给各种目标设定量像 `is_step_signal_` 标志位一样可以阶跃响应呢？

这引出了一个更干净的设计方向：

- 不再让 `is_step_signal_ / is_sine_ / is_hand_input_` 这种全局布尔量硬控所有目标
- 而是抽象成统一目标生成器 `buildDebugSetpoint(...)`
- 并将舵向和轮向的目标生成模式分离

因此后来又设计并推进了：

- `DebugSignalMode`
- `steer_signal_mode_`
- `drive_signal_mode_`
- `steer_hand_input_`
- `drive_hand_input_`
- `debug_step_threshold_`

这样你就可以：

- 舵向跑阶跃、轮向走摇杆
- 舵向固定手输、轮向跑正弦
- 两边都走摇杆
- 两边都走阶跃

这比单纯一个 `is_step_signal_` 的总开关要灵活得多。

### 5.9 关于“舵向校准零点下沉到电机层”的讨论

这是本次所有设计讨论里最有价值的一次。

用户观察到一个真实问题：

- 舵向电机校准完成后，发给电机的指令总要加减一个补偿量
- VOFA 打印时又要再减回去
- 这种写法非常冗余

这其实是架构层面的问题，不是数学层面的小问题。

根源是：

- 电机内部仍然活在“原始编码器角度坐标系”里
- 上层调试和人脑理解用的是“校准后的舵轮坐标系”

于是就会出现：

- 发指令时为了让电机理解，需要 `+ calibration_offset`
- 打印时为了让人理解，需要 `- calibration_offset`

这会导致长期维护困难，因为任何看代码的人都得不断追问：

- 这里为什么要加？
- 那里为什么要减？
- 这个值到底是原始坐标，还是校准后坐标？

于是提出了更好的方案：

- 在校准完成时直接调用 `relocate_totalAngle(...)`
- 从那一刻起，让电机对象自身就活在校准后坐标系里
- 上层所有角度命令和打印都直接使用校准后坐标系

这个方案在理论上是最干净的，也是后续推荐继续完成的方向。

### 6.1 单轮舵向 + 单轮轮向的对象绑定能力

从初始化链路可以看出，系统已经具备如下能力：

- 能将一个 DJI 舵向电机传给 `FourSteerChassis`

- 能在 `WheelConfig` 中同时持有两者句柄

### 6.2 `VESC` 在当前工程里的接入能力

- 通过扩展帧发送电流命令
- 解析 `STATUS_1`
- 将 `eRPM -> rpm_`

这意味着：

### 6.3 单舵轮调试时的命令下发逻辑

2. 生成舵向目标
3. 生成轮向目标
4. 根据调试模式选择给舵向电机下：

5. 给轮向 VESC 下目标 RPM
6. 运行光电门校准流程

也就是说，这已经不是“零散的测试代码”，而是一个有明确数据流的调试小系统。

### 6.4 VOFA 打印能力

- 尾部自动补 `JustFloat` 标识尾帧

## 7. `FourSteerChassis` 当前调试链路逐行解释

这一章的目标是让后续接手者不只是“看过函数”，而是真正知道这段函数的意图和副作用。

### 7.1 入口：`isDebugMode()`

`isDebugMode()` 的使用前提是 `is_debug_ == true`。

在当前 `FourSteerChassis` 里，这个标志默认就是 `true`，说明设计目标本身就是“当前这个类主要用于调试单轮流程”，而不是最终全功能舵轮控制器。

### 7.2 遥控器输入读取

函数开头先做：

- 通过 `CrsfReceiver::GetInstance(&huart7)` 获取接收机实例
- 调用 `receiver->getControlData(&airjoy_data_)`

于是你后面可以直接用：

- `airjoy_data_.right_x`
- `airjoy_data_.left_y`

等量来生成调试目标。

这里很重要的一点是：这个读取不是“事件式回调”，而是控制线程中主动拉取，所以接手者如果怀疑摇杆值不变，不能只查 `chassis.cpp`，还要回看 `Module_CrsfReceiver` 的初始化和串口 DMA 状态。

### 7.3 `debug_mode_` 与“上半段底盘模式切换”

在单轮舵轮调试逻辑之前，其实函数前半段还保留了一套“底盘模式切换”：

- `setTargetBodySpeedMode(...)`
- `setTargetWorldSpeedMode(...)`
- `setTargetBodySpeedLockNowRotZMode(...)`
- 等等

从目前单轮调试角度看，这一段不是主角，但它说明了：

- `FourSteerChassis` 当前文件不是纯粹只服务单舵轮测试的 demo
- 它保留了底盘级模式结构，只是核心运动学还没有完全展开

换句话说，后续如果要把单轮调试慢慢演进成整车舵轮底盘，这一段是可继续延伸的，而不是完全推翻重写。

### 7.4 单轮对象的选取

当前调试逻辑默认取：

- `auto &wheel = wheel_config_[debug_wheel_index_]`

目前 `debug_wheel_index_` 在 `FourSteerChassis` 中默认是 `0`。

这意味着：

- 当前所有舵向/轮向目标都只作用在 0 号轮
- 如果要切到别的轮，只需要改这个索引
- 但前提是 `Setup_ConfigInit.cpp` 里对应轮子的 `steer_motor_h[i] / drive_motor_h[i]` 必须真的已经绑定好

### 7.5 舵向目标生成

当前已经引入统一目标生成器思路：

- `buildDebugSetpoint(mode, axis, amplitude, hand_input)`

从语义上说，它接收四类信息：

1. 当前模式是摇杆、阶跃、正弦还是手输
2. 当前用哪个摇杆轴当输入
3. 本次目标的幅值上限是多少
4. 如果是手输模式，手输值是多少

于是舵向目标可写成：

- 摇杆模式：`right_x * debug_input_`
- 阶跃模式：`right_x` 超阈值则输出 `±debug_input_`
- 正弦模式：生成时间函数
- 手输模式：直接等于手输值

这比过去那种把 `is_step_signal_ / is_sine_ / is_hand_input_` 和摇杆轴硬写在一起更清晰。

### 7.6 轮向目标生成

轮向目标本质上和舵向完全平行：

- 输入轴换成 `left_y`
- 幅值参数换成 `drive_debug_input_`
- 手输值换成 `drive_hand_input_`
- 模式换成 `drive_signal_mode_`

这意味着接手者后续如果要扩展例如：

- 轮向也做阶跃电流模式
- 轮向做速度正弦响应
- 舵向固定某角度而轮向做阶跃速度扫描

在结构上已经有地方挂，不需要再发明新体系。

### 7.7 舵向执行模式

当前舵向执行模式仍由一组布尔位控制：

- `is_wheel_speed_mode_`
- `is_wheel_current_mode_`
- `is_wheel_single_position_mode_`
- `is_wheel_total_position_mode_`

这意味着目标生成器负责的是“生成一个抽象目标值”，而这四个布尔位决定的是“这个目标值被解释成什么物理量”。

例如同一个 `steer_target = 90`，在不同模式下意义不同：

- 速度模式：90 rpm
- 电流模式：90 A 或对应标度量
- 单圈位置模式：90 deg
- 多圈位置模式：90 deg total-angle frame

这也是为什么接手者做实验时一定要明确当前模式，而不能只看某个 `VOFA` 通道数值。

### 7.8 光电门校准状态机

当前校准逻辑大致是：

1. `is_power_on_cailbration_` 被触发时，进入 `is_doing_cailbration_`
2. 记录上一次光电门状态 `last_photogate_signal_`
3. 让舵向电机以 `cailbration_rpm_` 转动寻找边沿
4. 一旦当前光电门状态和上一时刻不同，认为穿过参考位
5. 停止电机
6. 在这一瞬间记录或重定义校准参考角

注意，这个状态机不是“很严格的工业级校准流程”，而是一个非常适合台架调试的轻量实现。它的优点是：

- 简单
- 好读
- 好改
- 和当前单轮调试线程自然集成

它的缺点是：

- 依赖固定方向、固定速度转动
- 对抖动、误触发、上电姿态容错有限
- 多轮并发校准时可能不够优雅

但在你现在这个“先单轮打通”的阶段，它是合理的。

### 7.9 为什么当前 `drive_target_rpm` 在校准时被压成 0

这是一个很务实的设计：

- 校准时你正在找舵向参考位
- 如果这时轮向电机还在持续转，会让台架调试变乱，也增加危险性

因此在校准进行中，直接把 `drive_target_rpm = 0.0f`。

这个处理很值得保留。

如果未来要改，也应该有明确理由，比如：

- 想做“边转舵向边给轮向小速度”的特殊实验
- 或者你已经有足够好的机械固定方案

否则不建议轻易改掉。
## 8. 当前 VOFA 打印通道的真实含义与局限

这一章非常重要。因为大量“我看到的值不对”问题，本质上不是控制错了，而是对打印通道的语义理解错了。

### 8.1 当前打印链路的发送方式

当前使用的是：

- `Debug_Printf::printf_DMA_JustFloat(...)`

它会：

1. 直接把 `float` 数组按二进制拷到发送缓冲区
2. 在末尾追加 `0x00 0x00 0x80 0x7F` 尾帧
3. 走 UART DMA 发出

这意味着：

- 上位机看到的通道顺序，严格等于数组里元素顺序
- 不存在“变量名自动跟过去”的机制
- 只要你换数组顺序，VOFA 图就会换语义

所以每次改打印顺序，最好同步记录一份“当前通道表”。

### 8.2 这次扩展后的打印目标

用户后续明确提出，希望在 VOFA 中看到：

- 光电传感器情况
- 舵向电机校准角度
- 舵向电机目标/反馈：
  - 电流
  - 速度
  - 单圈角
  - 多圈角
- 轮向电机目标/反馈：
  - 电流
  - 速度
  - 单圈角
  - 多圈角

于是打印帧扩展成了 18 个通道的大数组。

### 8.3 舵向部分为什么是可靠的

因为舵向电机是 `M3508`，而当前 DJI 电机层已经稳定提供：

- 目标电流
- 反馈电流
- 目标速度
- 反馈速度
- 目标单圈角
- 反馈单圈角
- 目标多圈角
- 反馈多圈角

换句话说，对于舵向电机，这些 VOFA 通道大多数都有真实意义。

### 8.4 轮向部分为什么不能一视同仁

轮向用的是 `VESC`。当前驱动里：

- 速度反馈有
- 电流反馈有
- 占空比反馈有
- 角度反馈没有真正打通

所以你要把当前轮向相关通道分成两类：

#### 真正有参考意义的：

- 轮向目标电流
- 轮向反馈电流
- 轮向目标速度
- 轮向反馈速度

#### 形式上能打印，但当前不能当成真实反馈的：

- 轮向目标单圈角
- 轮向反馈单圈角
- 轮向目标多圈角
- 轮向反馈多圈角

原因不是打印错，而是底层驱动没有把真实角度状态更新到 `Motor_Base` 那几个角度字段里。

### 8.5 因此接手人应该怎么解释 VOFA 图

如果你在当前板上看图：

- 舵向目标/反馈角速度、角度、电流有明显变化，这通常是可信的。
- 轮向速度、电流变化可信。
- 轮向角度四个通道如果一直是 0、固定值或者无规律，不要先去怀疑打印格式，先确认 `VESC` 驱动是否真的提供了角度解析。

### 8.6 当前通道管理的建议

建议后续接手人维护一份固定表，例如：

1. photogate
2. calibration reference
3. steer target current
4. steer feedback current
5. steer target rpm
6. steer feedback rpm
7. steer target angle
8. steer feedback angle
9. steer target total angle
10. steer feedback total angle
11. drive target current
12. drive feedback current
13. drive target rpm
14. drive feedback rpm
15. drive target angle
16. drive feedback angle
17. drive target total angle
18. drive feedback total angle

并在任何重排、增删通道时同步更新记录。

这在多人协作时非常有用。否则极容易出现：

- 你以为自己在看“目标速度”
- 另一个人以为这条曲线是“反馈电流”

最后两个人对同一张图得出完全不同结论。

## 9. 当前单舵轮调试逻辑中的优势与问题

### 9.1 已有优势

#### 优势一：链路完整

从摇杆到目标值，到电机指令，再到反馈，再到 VOFA，整条链路已经形成闭环观察能力。

这比那种“只能发指令，但看不到反馈”或者“只能看反馈，但没有方便下发目标”的调试方式强很多。

#### 优势二：舵向和轮向被真正分离

舵向、轮向各自有目标生成、各自有对象、各自有打印维度。

这非常适合调试，因为它避免了“所有问题都缠在一起”。

#### 优势三：模式切换足够灵活

在当前设计下，你已经可以逐步做：

- 摇杆直控
- 阶跃响应
- 正弦扫描
- 手动固定值

这对 PID 调参非常友好。

#### 优势四：校准流程已经嵌在同一线程里

虽然这会让函数显得有点长，但对现场调试来说反而方便：

- 一开线程，接收输入、校准、发命令、打印都在一个地方
- 不用在多个任务间来回跳

### 9.2 当前主要问题

#### 问题一：`isDebugMode()` 职责过多

它同时负责：

- 读遥控器
- 生成底盘级目标
- 生成单轮目标
- 控舵向
- 控轮向
- 校准状态机
- 打印

这在台架调试阶段还能接受，但如果后续继续演进，建议拆成几个更专一的辅助函数：

- `updateDebugInputs()`
- `updateSteerCalibration()`
- `applySteerDebugCommand()`
- `applyDriveDebugCommand()`
- `emitDebugFrame()`

#### 问题二：`VESC` 角度反馈缺口会误导人

如果不明确写出来，接手人很可能默认：

- `Motor_Base` 里有 angle，那它一定真能用

这是不对的。

必须明确：**当前 `VESC` 的角度相关 VOFA 通道只是接口层面存在，不代表反馈链路真实成立。**

#### 问题三：校准零点语义虽然讨论清楚了，但后续维护风险仍然存在

即使你最终把零点下沉到电机层，也仍然要写清楚：

- 光电门高电平对应的校准姿态到底定义成多少度
- 为什么是这个值
- 这个定义和机械装配参考位之间是什么关系

否则过几周之后，别人看到 `-180` 还是会问“为什么不是 0”。

#### 问题四：部分调试字段已经处于“迭代中间态”

本次对话中，调试字段从：

- `is_step_signal_ / is_sine_ / is_hand_input_`

演进到：

- `steer_signal_mode_ / drive_signal_mode_ / hand_input 分离`

所以接手人要特别警惕一个现象：

- 旧字段可能还存在于类里
- 新字段也已经存在
- 但不代表所有旧字段都已经完全从所有路径中清除

换句话说，后续继续清理时，要避免出现“新旧两套调试语义同时保留但只有一半真的在用”的状态。
## 10. 关于“舵向校准零点下沉到电机层”的完整设计讨论结果

这一章专门把这件事写清楚，因为它是本次工作里最可能继续推进的结构性优化。

### 10.1 当前原始写法为什么让人难受

在旧写法中，通常会出现类似逻辑：

- 发给电机角度命令时：
  - `steer_target += cailbration_angle_deg_`
- 打印给人看时：
  - `target_angle_print = raw_target - cailbration_angle_deg_`
  - `current_angle_print = raw_feedback - cailbration_angle_deg_`

这种写法虽然数学上可以成立，但工程上有几个问题：

1. **认知负担大**
   - 任何一个阅读者都要先问“当前变量到底是原始角度还是校准后角度”。
2. **容易漏补偿**
   - 你在一个地方记得加了，在另一个打印点忘了减，图就会错。
3. **调试和执行语义分裂**
   - 机器实际执行的是 A 坐标系
   - 人看到的是 B 坐标系
   - 这会让“控制有问题还是显示有问题”变得难分辨。
4. **后续扩展会指数级变乱**
   - 一旦再加自动路径、整车解算、四轮同步角度优化，这种散落补偿会非常难维护。

### 10.2 为什么 `relocate_totalAngle(...)` 是更好的切入点

从 `Motor_DJI.h` 的实现可以看出，`relocate_totalAngle(...)` 做的不是“显示偏置”，而是：

- 重新定义编码器累计总角度的参考零点
- 同时更新 `totalAngle_`
- 再由它推导出新的 `angle_`

也就是说，它能做到一件更本质的事：

> 从这一刻开始，让电机对象自己认为“当前这个姿态就是我定义的新零点/新参考位”。

这就非常适合舵向光电门校准。

### 10.3 讨论中达成的推荐方向

推荐方向不是“把补偿量换个名字继续传来传去”，而是：

- 光电门校准完成后，当场重定位电机零点
- 后续所有舵向角度命令和打印全部直接使用校准后坐标系

这样后续角度相关问题会简单很多：

- 你发 `90`，机器目标就是去 `90 deg`
- 你看打印 `90`，含义就是当前舵轮坐标系下的 `90 deg`
- 不需要每次再想“这个 90 是不是其实内部对应 263.7”之类的问题

### 10.4 两种可选实施层级

在讨论里，其实存在三层可能性：

#### 方案 A：只优化打印层

- 电机仍活在原始坐标系
- 发命令时继续补偿
- 只是打印时统一做转换

优点：
- 改动最小

缺点：
- 没有解决根问题
- 只是让人看起来舒服一些

#### 方案 B：底盘层统一封装 raw <-> calibrated 转换

- 不改电机对象内部零点
- 但在 `FourSteerChassis` 内建立一组明确 helper：
  - `rawToCalibrated(...)`
  - `calibratedToRaw(...)`
- 所有命令和打印只走 helper

优点：
- 比散落加减补偿干净很多

缺点：
- 仍然是两套坐标系并存
- 只是变成“集中补偿”，不是“消灭补偿”

#### 方案 C：电机层直接改零点

- 校准完成后立即 `relocate_totalAngle(...)`
- 后续只用校准后的舵轮坐标系工作

优点：
- 概念最干净
- 长期维护最好
- 扩展到整车时最不容易炸

缺点：
- 要谨慎确认“校准完成时到底把当前姿态定义成多少度”
- 如果对电机层零点语义理解不透，容易一开始改错

最终推荐的是 **方案 C**。

### 10.5 校准后姿态到底定义成多少度

这里不是代码问题，而是机械和语义问题。

在讨论中，默认保持当前语义：

- `photogate_signal_ == false` 时，当前姿态定义为 `0 deg`
- `photogate_signal_ == true` 时，当前姿态定义为 `-180 deg`（或等价 `180 deg`）

为什么会有这个二选一？

因为光电门只能告诉你“我触发了/我没触发”，但不能单独告诉你“你现在到底在这条轴的哪一端定义为正方向”。因此系统需要人为约定：

- 当光电门状态为某一值时，这个姿态在舵轮坐标系里该映射为多少角度

如果以后机械同学明确说：

- “光电门高电平时，这个朝向我们更想定义成 0 度，而不是 -180 度”

那么你不需要推翻整个架构，只要改：

- 校准完成时写入 `relocate_totalAngle(...)` 的那个参考值

这也是电机层零点方案的一个额外好处：语义修改点集中。

### 10.6 为什么建议分两步迁移

在讨论时还提出过一个很稳妥的过渡策略：

#### 第一步
- 校准完成时先调用 `relocate_totalAngle(...)`
- 同时把 `cailbration_angle_deg_` 置零
- 暂时保留旧的 `+/- cailbration_angle_deg_` 写法

结果就是：
- 旧代码逻辑仍在
- 但补偿量退化为 0
- 风险最小，方便确认“零点重定位是否本身正确”

#### 第二步
- 确认运行正确后
- 再删除所有补偿逻辑
- 把打印、注释、变量语义统一成“校准后角度”

这个两步法非常适合板边调试，因为它能把问题空间切开：

- 如果第一步就错，说明 `relocate_totalAngle(...)` 用法或参考角定义错了
- 如果第一步对、第二步错，说明是你清理补偿时逻辑断了

这比一步全改更利于定位。

### 10.7 当前需要警惕的一个现实问题

虽然这个方向已经讨论清楚，但从本次交接时的代码状态来看，**相关优化并不一定已经完全收口为最终版本**。

原因包括：

- 中间有过多轮尝试
- 有过用户打断
- 有过编码导致的修改困难
- 有过“先加 helper、再删旧逻辑”的阶段性中间态

因此，接手者在继续推进这一块时，一定要做两件事：

1. 不要只看设计说明，先搜索代码里是否还残留：
   - `steer_target += cailbration_angle_deg_`
   - `target_angle - cailbration_angle_deg_`
   - `current_angle - cailbration_angle_deg_`
2. 在板子上直接验证：
   - 校准完成后当前角是不是已经真的变成你定义的参考角

只有这两件都成立，才说明“零点下沉到电机层”真正完成了。

### 11.1 风险点一：关于当前磁盘代码与讨论目标的差距

虽然这次对话中已经明确讨论了很多优化方向，但当前接手人必须时刻记住：

- **某个 helper 已经加了 ≠ 所有旧逻辑都已经清掉了**
- **VOFA 通道已经扩了 ≠ 每个通道都真的有物理意义**

因此接手第一步不是“继续写新功能”，而是“把现状定格”。

   - `relocate_totalAngle`
   - `steer_target +=`

   - 旧补偿逻辑还在
   - 新 helper 已经有了
   - 零点重定位是否真的落在校准完成分支里

### 11.2 风险点二：VESC 角度打印极可能误导

这是非常容易坑人的地方。

当前轮向 `VESC` 的速度、电流反馈可以用，但角度反馈链路没有真正打通。于是：

- 轮向目标角度通道可以有值，因为目标量本来就能写
- 轮向反馈角度通道可能没有真实意义

一旦接手者忘了这一点，很容易得出错误结论，比如：

- “为什么 VESC 角度跟不上目标？”
- 事实上不是跟不上，而是压根没解析角度反馈

所以建议：

- 调速阶段先盯轮向速度/电流
- 角度四通道先只当占位，不当诊断核心依据

### 11.3 风险点三：`isDebugMode()` 已经很强，但也已经很重

如果继续往里面塞：

- 更复杂的阶跃逻辑
- 多轮同步逻辑
- 自动测试序列
- 更多打印映射

那么它很快会从“方便调试”变成“难以维护”。

因此接手策略建议是：

- 如果只是再做一两次单轮实验，可以继续往里加少量逻辑
- 如果准备把它做成长期可维护的舵轮调试框架，应该开始拆辅助函数

建议的拆分方向前面提过，这里再强调一次：

- 输入读取
- 目标生成
- 校准状态机
- 执行命令
- 打印组帧

最好逐步从一个大函数拆成 4~5 个小函数。

### 11.4 风险点四：`Setup_ConfigInit.cpp` 中的临时注册策略不能忘记恢复

现在 `CAN2` 上旧武器侧电机注册之所以被暂停，是为了单舵轮台架调试方便。

这在当前阶段是合理的，但后续一旦切回整机集成测试，必须重新评估：

- 是否要恢复 `Weapon_*` 相关注册
- 是否要恢复 `DJIGroupCAN2_Low`
- 是否要将 VESC 与原业务共存
- 如果共存，总线负载和发包时序是否能接受

所以建议文档里明确记住一句话：

> 当前 `CAN2` 是“为了单舵轮调试而临时净空”的，不是最终整机架构的稳定终态。

### 11.5 风险点五：目标生成器与旧布尔开关可能并存

当前为了减少风险，存在一种可能中间态：

- 底盘上半段 `target_omega_z` 调试仍使用旧的 `is_step_signal_ / is_sine_`
- 单舵轮调试下半段已经开始使用 `buildDebugSetpoint(...)` 和独立模式

这不是错误，但意味着**风格暂时不统一**。

接手时要做判断：

- 你是只想继续把单轮调试做好？那可以先接受这种并存。
- 你是准备继续清理整个类的调试接口？那应当逐步把上半段也迁移到统一目标生成器体系。

### 11.6 推荐的接手顺序

如果明天由另一个同学继续接手，我推荐这个顺序：

#### 第一步：定格现状
- 看 `chassis.cpp/.h`
- 确认目标生成器、VOFA、校准逻辑、VESC 绑定都在什么状态

#### 第二步：板边验证最小闭环
- 校准一次
- 舵向单圈位置模式给几个典型角度
- 轮向速度模式给几个典型速度
- 看 VOFA 是否和肉眼现象一致

#### 第三步：决定是否继续推进“零点下沉到电机层”
- 如果当前代码还处于补偿/重定位混合态，就先收这件事
- 不要一边零点语义没统一，一边继续加复杂模式

#### 第四步：再谈更进一步的调试自动化
例如：
- 自动阶跃测试序列
- 固定时间窗口采样
- 自动切换目标模式
- 记录一组标准参数的响应结果

换句话说：**先统一坐标系，再追求调试自动化。**

## 12. 下一位接手者的具体工作建议

这一章给的是“工程师操作建议”，不是抽象原则。

### 12.1 如果你明天只想继续调 VESC 速度环

建议最小动作路径：

1. 确认 `CAN2` 上只挂了 `vesc_drive_101`
2. 确认 `STATUS_1` 在正常回传
3. 只看四个核心通道：
   - 轮向目标电流
   - 轮向反馈电流
   - 轮向目标速度
   - 轮向反馈速度
4. 忽略轮向角度四通道
5. 先用摇杆模式调手感
6. 再切到阶跃模式做速度环参数观察

### 12.2 如果你明天要继续调舵向单圈角位置环

建议重点盯：

- 光电门状态
- 当前角
- 目标角
- 目标速度
- 反馈速度
- 目标电流
- 反馈电流

注意：

- 位置环和速度环是套娃关系
- 即使目标角对了，如果内部速度环差，最终位置看起来也会“发飘”

所以调舵向位置环时，不要只看角度曲线，也要看速度和电流有没有异常放大或滞后。

### 12.3 如果你明天要继续推进“舵向零点下沉到电机层”

你应该先确认三件事：

1. `relocate_totalAngle(...)` 触发时机是否正确
2. 校准参考姿态到底应该写成 `0` 还是 `-180`
3. 旧补偿逻辑是否已经删干净

验证标准很简单：

- 校准结束后，不做任何额外补偿
- 直接发 `0 / 90 / -90 / 180`
- 如果机器和 VOFA 都能直接在同一坐标系下说话，那这件事就算真正成功

### 12.4 如果你明天要把单轮调试扩成多轮

先别急着“复制四份”。

建议你先回答：

- 光电门是每个舵向轮都有一套，还是现在只有测试位那一套？
- 每个轮子的参考姿态定义是否一致？
- 每个轮子舵向安装角、轮向正方向是否都相同？
- VESC 是只打一只轮，还是四只轮都要上？

如果这些问题还没明确，直接扩多轮会把问题放大四倍。

   - `M3508(ID=1) -> CAN1`
   - `VESC(ID=101) -> CAN2`

### 第 1 步：只验证，不改动

- 上电
- 校准一次
- 右 X 控舵向角
- 左 Y 控轮向速度
- 看 VOFA：
  - 光电门
  - 校准角
  - 舵向目标/反馈角
  - 轮向目标/反馈速度
  - 舵向与轮向目标/反馈电流

目的：先确认你理解的语义和板上实际现象一致。

### 第 2 步：如果 VESC 速度环是首要目标

- 不要先碰坐标系
- 不要先碰整车舵轮解算
- 只围绕：
  - `drive_target_rpm`
  - `drive_feedback_rpm`
  - `drive_target_current`
  - `drive_feedback_current`
  来调

### 第 3 步：如果舵向坐标系仍觉得别扭

- 回到“零点下沉到电机层”那条线
- 不要继续在上层再发明第三套补偿
- 要么彻底统一，要么暂时保持现状
- 最怕的是“补偿 A 还没删，又新加一个补偿 B”

### 第 4 步：每次改打印顺序都写注释

因为这套系统很依赖 VOFA，任何一次通道顺序变更都应该：

- 改代码里的数组顺序
- 改注释里的通道表
- 最好在 `_ai` 目录留下小备忘

## 附录 A：关键文件逐份阅读建议

这一附录不讲抽象结构，只讲“如果你打开某个文件，应该重点看哪些段落、为什么看它、看完后你应该回答哪些问题”。

### A.1 `User\Setup\Src\Setup_ConfigInit.cpp`

这是接手人最应该先看的初始化文件之一。阅读时建议按照下面顺序：

#### 第一段：总线对象实例化

看：

- `CAN1_Bus`
- `CAN2_Bus`
- `CAN3_Bus`

你要明确：

- 工程里三路 FDCAN 都是通过 `fdCANbus::getInstance(...)` 拿到的单例
- 后续任何电机对象都必须和某一路总线绑定
- 如果某个电机对象“看起来创建了但就是没帧”，先回头看它到底绑定到哪一路

#### 第二段：电机对象实例化

重点看：

- `omni_wheel1`
- `Weapon_*`
- `vesc_drive_101`（如果当前版本已经保留）

这里接手人应形成两层认识：

第一层是物理层：
- 这个对象映射的是哪台真实电机
- 它的总线和 ID 是多少

第二层是工程层：
- 这个对象会不会被后续控制器拿去当作“舵向电机”
- 还是会被当作“轮向电机”
- 还是只是原武器侧遗留对象

#### 第三段：`FourSteerChassis` 初始化配置

看 `Chassis::InitConfig chassis_init_config` 那一块时，不要只看值，要回答：

- `steer_motor_h[0]` 指向谁
- `drive_motor_h[0]` 指向谁
- 其余三个轮子是不是空
- 这是否意味着当前设计本来就是“单轮调试模式”而不是“四轮整车模式”

如果这里还是空指针，那么上层 `isDebugMode()` 再怎么改都不可能真正打通轮向。

#### 第四段：CAN 注册顺序

接手人必须养成一个习惯：**不要只看对象有没有 new 出来，要看有没有 register 到总线。**

当前在单舵轮调试语义下，你最应该确认的是：

- `CAN1_Bus` 上 `omni_wheel1` 还在不在
- `CAN2_Bus` 上 `vesc_drive_101` 在不在
- `Weapon_*` 和 `DJIGroupCAN2_Low` 是否被临时取消注册

这些信息如果看漏了，后续所有“为什么车轮不转/为什么总线有旧帧”类问题都会绕圈。

### A.2 `User\Setup\Inc\Setup_ConfigInit.h`

这个文件看起来只是 include 和声明，但它对编译能否过、类型是否完整也很关键。

建议重点确认：

- `Motor_VESC.h` 是否已经被纳入这里，而不是在 `.cpp` 顶部单独 include
- `chassis.h`、`WeaponSage_Setup.h`、`Arm_Setup.h` 这些上层对象是否都从这里汇总进来

原因是：

- 后续如果再有人加新的电机类或控制器类，最好沿着这里统一做依赖入口，而不是每个 `.cpp` 到处散加头文件
- 统一依赖入口虽然会让头文件略重，但对当前这种 Keil 嵌入式工程反而更容易管理

### A.3 `User\Setup\Inc\chassis.h`

这个头文件极其重要，因为它同时承载了两种底盘类。阅读时要刻意区分：

- 前半段是 `TriOmniChassis`
- 后半段是 `FourSteerChassis`

最容易犯的错是：

- 你以为自己加的是四舵轮字段，结果改到了三全向那一部分
- 你以为某个 `buildDebugSetpoint(...)` 是给四舵轮的，结果声明跑到了前半段

阅读建议：

1. 先找到 `namespace FourSteerChassis`
2. 从 `class Chassis` 开始往下看
3. 对下面这些块做标记：
   - `WheelConfig`
   - `InitConfig`
   - 调试参数区
   - 舵向 helper 声明
   - 轮向 helper 声明
   - 光电门校准相关字段

#### `WheelConfig` 的理解重点

- `smh` 是 steering motor handle
- `dmh` 是 drive motor handle

这个别名设计非常实用，因为后面读代码时：

- `wheel.smh` 一看就是舵向电机
- `wheel.dmh` 一看就是轮向电机

不需要在每一行都重新脑内翻译变量含义。

#### 调试参数区的理解重点

这里有几类参数：

- 开关型：如 `is_debug_`、某些模式布尔位
- 幅值型：如 `debug_input_`、`drive_debug_input_`
- 模式型：如后续引入的 `steer_signal_mode_`、`drive_signal_mode_`
- 校准型：如 `cailbration_rpm_`、`cailbration_angle_deg_`

你在继续接手时，最应该做的一件事，是把这些参数按“谁决定目标源、谁决定执行模式、谁只是诊断量”分类，不然之后一多就会乱。

### A.4 `User\Setup\Src\chassis.cpp`

这是当前你最核心的工作文件。建议阅读顺序不要从头扫，而是按下面几个小模块抓。

#### 第一块：`FourSteerChassis::init`

确认：

- 线程是怎么起的
- `wheel_config_[i]` 是怎么从 `InitConfig` 拷过来的
- 有没有对舵向电机做额外减速比修正

#### 第二块：舵向 helper 函数

例如：

- `setSteerWheelTargetRpm`
- `setSteerWheelTargetCurrent`
- `setSteerWheelTargetAngleDeg`
- `setSteerWheelTargetTotalAngleDeg`
- `getSteerWheelCurrentAngleDeg`
- `getSteerWheelCurrentRPM`
- `getSteerWheelCurrentCurrent`

这些函数的存在意义，是让后面 `isDebugMode()` 读起来像在说“业务语义”，而不是直接到处 `wheel.smh->...`。

#### 第三块：轮向 helper 函数

例如：

- `setDriveWheelTargetRpm`
- `setDriveWheelTargetCurrent`
- `getDriveWheelTargetRPM`
- `getDriveWheelCurrentRPM`
- `getDriveWheelCurrentCurrent`

这些函数是后来为了 `VESC` 单轮调试补出来的。

接手人要知道：

- 它们目前大多只是轻量透传
- 但它们是后续补轮向更多语义（例如角度反馈）最自然的挂点

#### 第四块：`buildDebugSetpoint(...)`

如果当前代码里已经有它，那么它是后续一切调试目标模式扩展的中心。

你要重点看清楚：

- 输入是什么
- 返回的量代表什么
- 哪些模式已经支持
- 阶跃阈值从哪里来
- 正弦频率和偏置从哪里来

#### 第五块：`isDebugMode()`

这一块一定要精读，因为它是当前单轮调试现场。

阅读时建议把它人工分段：

- RC 输入读取段
- 底盘模式/姿态锁定段
- 单轮目标生成段
- 舵向执行段
- 校准状态机段
- 轮向执行段
- VOFA 打印段

如果你按这个分法去理解，它就不会显得是一个完全不可维护的巨函数。

### A.5 `RC10_LIB\Motor\Inc\Motor_DJI.h`

你接手这份代码时，必须至少理解这里三件事：

1. `getAngle()` 和 `getTotalAngle()` 的语义差异
2. `setTargetAngle()` 与 `setTargetTotalAngle()` 的控制模式差异
3. `relocate_totalAngle()` 到底改了什么

其中第三件事是后续继续推进“舵向零点下沉到电机层”的关键。

### A.6 `RC10_LIB\Motor\Inc\Motor_VESC.h` 与 `Motor_VESC.cpp`

阅读重点不是看它写得多复杂，而是明确边界：

- 反馈实际解析了哪些状态
- 哪些只是接口存在，但还没有真实意义

尤其记住：

- 当前匹配的是 `STATUS_1`
- 真实可用的是速度和电流
- 不要默认轮向角度已经可用

### A.7 `RC10_LIB\APP\Inc\APP_debugTool.h`

接手人只要抓住一句话就够：

- `printf_DMA_JustFloat` 发的是“按顺序排列的裸 float 数组”

因此后续任何通道调整，都只是在改数组顺序，不是在改一个更复杂的协议层。
## 附录 B：板边调试时建议直接记录的数据与现象

这一附录的目标是帮助接手人做实验时“知道该记什么”。很多时候你不是不会调，而是没有记录对比材料，隔十分钟就忘了上一次发生了什么。

### B.1 校准实验建议记录模板

每次上电校准，都建议记一小段表格：

- 时间
- 舵向电机编号
- 光电门初始状态
- 校准开始前当前单圈角
- 校准开始前当前多圈角
- 校准转速设定值
- 校准完成后当前单圈角
- 校准完成后当前多圈角
- 当前你定义的参考姿态角度
- 备注（是否有抖动、是否一次成功、是否穿越边沿后又反跳）

如果以后你们有 4 个舵轮都要校准，这个表格非常有用，因为你能横向比较：

- 4 只轮子参考位是否一致
- 哪只轮子最容易误触发
- 哪只轮子最容易在边沿附近来回抖

### B.2 舵向单圈位置模式建议记录模板

对于 `0 / 90 / -90 / 180` 这类标准单圈角测试，建议记录：

- 目标角
- 到达时间
- 稳态误差
- 是否有明显超调
- 速度峰值
- 电流峰值
- 有无明显抖动

其中最值得看的不是某个单值，而是趋势：

- `0 -> 90` 和 `0 -> -90` 是否表现对称
- `90 -> 180` 和 `-90 -> -180` 是否表现对称
- 某个方向总是慢，说明机械摩擦或重力、接线方向、PID 参数可能不对称

### B.3 轮向速度阶跃建议记录模板

对于 VESC 速度调试，建议选几个固定阶跃值，比如：

- `+100 rpm`
- `+300 rpm`
- `+600 rpm`
- `-100 rpm`
- `-300 rpm`
- `-600 rpm`

每次记录：

- 目标速度
- 响应上升时间
- 稳态误差
- 最大反馈电流
- 是否出现明显振荡
- 正反向表现是否一致
- 中位回零时是否拖尾

### B.4 正弦测试建议

如果用统一目标生成器切到 `kSine`，建议先从低频开始：

- 小幅值、低频
- 再逐步增大幅值
- 再逐步增大频率

因为这样你可以先看：

- 系统有没有基础跟随能力
- 不是一上来就被高频打爆

记录时建议关心：

- 幅值衰减
- 相位滞后
- 是否在某频率附近开始明显跟不上

### B.5 建议现场同步录视频

对舵轮调试特别有帮助的一件事是：

- 上位机波形录屏
- 轮子实际动作手机录像
- 两者时间轴大致对齐

原因是有些问题仅看波形看不出来，比如：

- 电机明明到位了，但机械结构有松动
- 光电门其实有物理遮挡抖动
- 轮子方向切换时机械有反冲

而有些问题只看视频也看不出来，比如：

- 电流已经冲得很高
- 速度环一直在抖
- 目标和反馈之间其实有固定相位差

两者结合，效率会高很多。
