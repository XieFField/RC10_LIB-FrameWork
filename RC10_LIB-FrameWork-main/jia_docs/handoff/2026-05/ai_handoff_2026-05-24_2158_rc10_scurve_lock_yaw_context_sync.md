## 一句话总结

当前 RC10 底盘主线已经不是“先做故障探测、再尝试回退”的过渡态，而是进入了一个更完整的联调态：在保留舵向故障 gate、homing gate 和 `current=0` 保护不回退的前提下，把手操 S 形速度规划、锁航向继承语义、默认调试入口与现场参数一起对齐到同一条主线。

## 当前主线在看什么

这条线现在关注的不是单点功能，而是三个连续层次是否一致：

- 输入层：手操目标、调试入口、默认模式是否能稳定进入预期控制路径。
- 规划层：S 形成形、reverse intent、低速抑制、平移方向冻结是否互相打架。
- 保护层：舵向 fault gate、homing gate、锁存后 `current=0`、LockTo/LockNowYaw 之间的角度语义是否连续。

换句话说，这条主线的核心不是“能不能动”，而是“在异常、切换、近目标收尾、反向意图和调试切换时，行为是否还像同一个底盘”。

## 这几个提交各自解决了什么

### `9ee24074`：手操 S 形速度规划第二版

这个提交的语义变化最大。它不是给原有一阶限幅再包一层，而是把手操主链路的速度成形从“限斜率”升级成了“在线 jerk 受限跟踪器”。

它的关键变化有四个：

- 从 `shaped_rate` 语义升级为 `shaped_accel`，内部状态开始显式表示“加速度”，不再只是记录一个慢变量。
- 增加提前制动逻辑，让接近目标速度时不再硬顶到最后一拍，收尾更连续。
- 增加 settle 阈值和小残差安全贴合逻辑，贴近目标时会同步清零内部加速度状态，避免近零抖动和残留惯性。
- 保留 legacy 路径和运行时模式切换能力，所以它不是一次性替换，而是可回退、可对比、可在现场切换的双轨语义。

它的意义在于：手操速度不再只是“别跳太快”，而是“按加速度和 jerk 约束自然起、自然停、自然反向”。对联调现场来说，这会明显改善速度台阶、反向切换和近目标收尾的可读性，也更利于把问题区分成“输入问题、规划问题、保护门问题”。

### `2a2d1414` 与 `65de57aa`：默认参数和调试入口的现场影响

这两个提交看起来像参数调整，实际上是在对齐联调现场的“默认观察面”。

`2a2d1414` 做了两件事：

- 把低速驱动抑制的 `close_angle_deg` 默认值从 `1.0` 调到 `10.0`。
- 把 `debug_control` 的默认 `mode_raw` 从 `1` 调到 `2`。

`65de57aa` 在此基础上继续做了三类对齐：

- 把 `FOURSTEER_SINGLE_WHEEL_TRACE_UART8` 默认从 `1` 改成 `0`，默认关闭单轮 UART8 追踪，减少日常联调噪声。
- 把 `reverse_intent` 的角度门槛改得更早进入、更早退出：`enter_angle_deg` 从 `135` 到 `105`，`exit_angle_deg` 从 `105` 到 `75`。
- 再次把 `debug_control_.mode_raw` 默认置到 `2`，让现场默认从更合适的调试入口进来。

对联调现场的影响可以直接理解为：

- 默认调试入口更接近当前主线要看的模式，少走绕路。
- 低速抑制更容易被触发，现场更容易看到“方向不对时驱动被压下去”的保护效果。
- 反向意图更早介入，也更早退出，利于观察手操 S 形下的自然卸载和翻向趋势。
- UART8 默认关掉后，现场不会被无关追踪流淹没，但也意味着排查单轮问题时要明确把追踪入口再打开。

所以这两条不是单纯“改默认值”，而是在给联调现场换一个更贴近当前主线的观察坐标系。

### `9be82103`：`LockToYaw -> LockNowYaw` 锁角继承修复

这个修复解决的是一个很容易在现场被误判的问题：`LockToYaw` 切回 `LockNowYaw` 时，锁角没有继承“当前真正生效的锁角”，而是可能回到旧值，或者重新抓 IMU 当前角，导致切换瞬间的锁航向语义跳变。

修复点很直接：

- 在 `isLockToRotZ(...)` 里，计算出本周期真正生效的 `out_rot_z` 后，立即写回 `lock_now_rot_z_target_`。
- 同时把 `lock_now_rot_z_shift_count_` 清零，避免切回 `LockNow` 的首拍误入重新抓当前 IMU yaw 的过渡分支。

它修的是“模式切换时锁角继承”而不是“PID 能不能跟上”。这个区别很重要，因为现场看到的现象会像是锁角乱跳，但根因其实是状态继承错了。

回归测试的证明方式也对应这个语义：

- 先把 `lock_now_rot_z_shift_count_` 置为非零。
- 再进入一次 `LockToYaw`，让它产生一个与当前 IMU yaw 不同的有效锁角。
- 断言 `LockTo` 已把这个有效锁角写回 `lock_now_rot_z_target_`，并清零 shift 计数。
- 然后立即切回 `LockNowYaw`，断言它继承的是刚刚那个有效锁角，而不是重新抓取当前 IMU yaw。

这说明回归测试验证的是“有效锁角连续性”，不是只看输出有没有动。

### `9048c971`：把 S 形手操速度规划并回故障恢复主线

这个 merge 提交是整条线真正合并后的状态说明。它的重点不是“把分支合进来”这么简单，而是“合进来以后仍然不退回故障保护语义”。

它做了三件关键事：

- 保留主线已有的舵向故障检测、锁存、恢复、rehome 与 PID 清理保护语义。
- 引入 `9ee24074` 的手操 S 形速度规划第二版，包括 `ManualSpeedProfileMode`、`JerkLimitedAxisState` 以及运行态辅助接口。
- 在 `chassis.h` / `chassis.cpp` 冲突处手工融合，确保 S 形规划不会绕过 steer fault gate、homing gate 和 `current=0` 保护。

这也意味着：

- S 形规划是并入主线，不是另起一条旁路。
- fault gate 不是被“先规划再说”这种方式冲掉的。
- 现场如果碰到异常，仍然应该先按故障恢复主线去判断，而不是把 S 形本身当成新问题源头。

另外，`9048c971` 还保留了一个很重要的补充修正：在 `SCurve` 模式下，快速反向输入不会直接被 reverse intent 快捷分支覆盖，而是要先让速度自然卸载，再建立反向趋势。这个细节能避免“反向一来就硬拐”的观感，也避免把规划层的收尾逻辑直接抹掉。

## 后续排查重点

后面如果继续查问题，优先盯这几个点：

- `SCurve` 模式下的近目标收尾是否稳定，尤其是 `settle` 之后内部加速度是否真的清零。
- 快速反向时，reverse intent 和 jerk 受限成形是否仍保持一致，不出现“规划刚收口，意图又抢跑”的情况。
- `LockToYaw` 切回 `LockNowYaw` 时，锁角继承是否始终跟随“有效输出”而不是“旧目标”或“当前 IMU”。
- 调试默认入口与低速抑制参数是否只是适合当前联调现场，还是已经需要重新分层成可配置项。
- fault gate 相关路径是否仍然优先于任何手操成形逻辑，尤其是在舵向异常、homing 未完成或恢复阶段。
